# CVB Builder ADR — build/release boundary, delta posture, template drift, and the concept-id interval contract

This is CVB's first design record and establishes the convention: descriptive `<topic>_ADR.md` files under a flat `docs/architecture/`, mirroring the enterprise repo's pattern (no numeric prefixes) so cross-repo readers find design records in the same place under the same naming. Introduce per-topic subdirectories when a second topic needs one.

Status: **Accepted 2026-07-23** (Daniel; sign-off "commit it" after five review rounds). Two open questions remain recorded below with default postures — neither blocks this ADR's rulings. Drafted 2026-07-16; updated 2026-07-23 to record events since (cleanup merge as PR #3 with empirical gate passed, promote merged as PR #4, the EU2-baseline out-of-scope ruling and D2 provenance-completeness gate, two new export findings, and Daniel's D9 resolution-model ruling: NS-only automated mint, one concept per source code, zero by omission, with custom standard-minting reserved as a deliberate future capability). Standing design address: atlas node `cvb-builder-adr` (see Consult protocol at the end).

## Context

CVB (Custom Vocabulary Builder) turns per-package SSSOM `mapping.csv` sheets into custom OMOP concepts (the 2-billion id space) and delta CSVs consumed downstream. The repo has had no design authority: the build (`<VOCAB>/Builder/execute-pipeline.sh`, dockerized Postgres, shared SQL at `Builder/sql/shared/`) and the release (`scripts/package-release.sh` + `.github/workflows/release-vocab.yml`, which zips `<VOCAB>/Ontology/`) are disconnected for modern packages; `_TEMPLATE/` has drifted below the one live package (`EU2_Flowsheets`) it is supposed to seed; and an undeclared concept-id interval contract produced a whole bug class (#606, #609: the empty interval `[NS_RANGE_MIN, ID_RANGE_MAX]`, empty by construction because `new-vocab.sh` sets `NS_RANGE_MIN = ID_RANGE_MAX`).

Historical shape, established from code and git history: the archived vocabs (`.GIS`, `.MIMIC`, `.PSYCHIATRY`) committed their full `Ontology/*.csv` delta sets to git via a self-hosted-runner CI that ran the pipeline, copied `/tmp/output/*` into `Ontology/`, and pushed each file back through the GitHub content API as `omop-vocab-builder[bot]` (`git-integration.js`). The modern dockerized pipeline dropped the copy-back step entirely: `execute-pipeline.sh` ends at `/tmp/output/`, `EU2_Flowsheets/Ontology/` holds only a `.gitkeep`, and a release cut today would ship an empty zip (#607).

Downstream contract (enterprise `datamappings_ingest_ADR.md`, decision D7): the Emory concept surface is "Original ⊕ Delta → Merged" — immutable versioned Athena bundles, plus CVB Builder deltas as versioned additive artifacts, merged in `EmoryOMOPVocabulariesIngest`. 2B ids are stable forever once used. The enterprise ADR explicitly names CVB's `id-registry.csv` as the allocation authority.

The branch `chore/cvb-builder-cleanup` (held uncommitted pending this ADR's rulings, then merged 2026-07-16 as PR #3 once ruled) fixes the empty-interval bugs, hardens the bind-mount cleanup, back-ports `author_label` fixes to `_TEMPLATE`, and originally proposed an unconditional `cp /tmp/output/* <VOCAB>/Ontology/` tail step in the build (dropped per D3). Its disposition is recorded file-by-file below.

## Out of scope

The **datamappings-ingest surface** is not redesigned here: `EU1_CDW/Mappings/mapping.csv`, `EU2_Flowsheets/Mappings/mapping.csv`, `scripts/validate-mapping-csv.py`, `scripts/cvb_constants.py`, and `scripts/package-mapping-release.py`. That track owns its own ADR (enterprise `datamappings_ingest_ADR.md`) and is April-gating.

Classification only: `scripts/package-mapping-release.py` is the **sheet-release surface** — it releases the mapping *input* (curated SSSOM sheet → trimmed 23-column CSV → versioned S3 → `omop_etl.src_mapping_sssom`). The Builder's delta release, governed by this ADR, is the **delta-release surface** — it releases the minted *output* (concepts, relationships, ancestors, synonyms). These are two releases of two different artifacts with different consumers, and both are legitimate. Post-April unification of their versioning/trigger machinery is fair game for a future consult; nothing in this ADR changes the sheet-release path.

Also out of scope: the FCA/methodology tooling under `EU2_Flowsheets/`, the Streamlit mapping-contributor app, and the in-flight provenance-tagging WIP on the main checkout (see Open questions).

## The central tension, resolved

Two true observations point at the same conclusion (commit the deltas) for different reasons, and the reason decides the Q1 mechanism.

Observation A (build non-determinism): concept_id assignment consults live `vocab.concept` state, hands out ids with no `ORDER BY` (`update-standard.sql:37-52`), and stamps `now()::date` — so a from-scratch rebuild does **not** reproduce previously published ids. The committed deltas are therefore the only durable record of which concept_id each source code received.

Observation B (designed lifecycle): the pipeline is built as rebuild-from-mappings against DB state — `hard-reset.sql` deletes all ≥2B rows, `evaluate-difference.sql` excludes already-existing codes, the id sequence resumes from existing minima, `restore.sql` is "not required for ingestion", and `scripts/diff-deltas.sh` exists precisely to compare a fresh build against the committed `Ontology/` copy (in intent — its current implementation falls short of a real drift gate; see D6.5).

Resolution: **both are right, at different layers.** The *working* id authority is the live `vocab.concept` state; the *durable* id authority is the committed delta set, because the Docker volume is disposable by design (hard-reset.sql's existence proves the DB is treated as rebuildable) and the build cannot regenerate ids from mappings alone. The lifecycle is: seed the DB with the committed custom concepts, run the build incrementally against that state, and the build is id-stable; run it against an unseeded DB and it silently re-mints. This means the committed `Ontology/` directory is not merely a distribution convenience — it is the **id-registry-of-record** for minted concepts (the row-level complement to `id-registry.csv`'s range-level authority).

The Q1 consequence follows directly: precisely *because* `Ontology/` is the registry-of-record, the build must not write to it unilaterally. A pipeline step that can produce corrupt output (the duplicate-on-rerun class this ADR's own interval fixes address) must not have unattended write access to the record surface. Promotion into `Ontology/` crosses a gate — the drift diff plus a human commit — and is a release act, not a build step. That is also the transferred principle from the enterprise `kitchen_vs_release_ADR.md`: a refresh is not a release (§3.7); the build engine is shared enablement a release consumes, not the thing that writes the release (§3.6).

## Decisions

### D1 — ADR home and design authority

**Decision.** This ADR lives at `docs/architecture/cvb_builder_ADR.md` in the CVB repo. The atlas node `cvb-builder-adr` is the standing design address for CVB Builder questions (Consult protocol below). Future CVB ADRs join it under `docs/architecture/` with descriptive `<topic>_ADR.md` names.

**Rationale.** No `docs/`, ADR directory, or design record exists anywhere in CVB on any branch; the closest prior art is process docs (`.MIMIC/Ontology/readme.md`, FCA methodology). The enterprise repo's convention (descriptive `*_ADR.md` under `docs/architecture/`) is the house style; matching it costs nothing and buys cross-repo findability.

**Consequences.** Creates `docs/architecture/`. `README.md` gains a one-line pointer to the ADR. Design questions raised mid-implementation get filed as consults against `cvb-builder-adr` instead of being decided in PR bodies.

**Alternatives rejected.** `Builder/README-design.md` (buries repo-wide decisions inside one component); `docs/adr/0001-*.md` numeric style (contradicts the enterprise convention this org already uses); keeping decisions in the enterprise repo (CVB is consumed by external parties — TuftsCTSI lineage, public releases — so its design record belongs with its code).

### D2 — Delta CSVs are committed to git; committed `Ontology/` is the id-registry-of-record and the release source

**Decision.** Each vocabulary's delta CSVs (`concept_delta.csv` and companions, `mapping_metadata.csv`, `source_to_concept_map.csv`) are **committed to git** under `<VOCAB>/Ontology/`. The committed set is (a) the durable row-level id registry — the authoritative record of which concept_id each source code received, complementing `id-registry.csv`'s range-level authority — and (b) the sole input to the release packager. `restore.sql` and `update_log.csv` are committed alongside as build provenance but are explicitly not part of the consumer ingestion contract. `.gitignore` stays as-is (`output/` and `release/` ignored; `Ontology/` tracked). **Provenance-completeness gate:** a committed `Ontology/` baseline requires complete SSSOM provenance on its source mappings — `mapping_justification`, author, confidence, human-confirmation status, and the recorded reasoning behind each judgment — not merely a successful build; promotion (D3) gates on provenance completeness as well as drift. Delta CSVs cannot supply provenance the mapping sheet never carried, so the gate is evaluated against the source `mapping.csv`, before the build, not against the output. Two verified export-set inconsistencies qualify what "the delta set" currently means and must be fixed in the export chore (see backlog): `concept_relationship_metadata_delta` is created by `create-delta-tables.sql` but exported by neither the CSV loop nor `restore.sql` — a delta table that silently never ships; and `domain_delta`/`relationship_delta` ship as CSVs but are absent from `restore.sql`'s `pg_dump` table list, so `restore.sql` does not round-trip the full delta set — one more reason it is provenance, not the record, and why D6.3's seed path must load from the CSVs, never from `restore.sql`.

**Rationale.** Four independent lines of evidence converge: the build is non-deterministic (unordered `nextval`, `now()::date`), so published ids are unrecoverable from mappings alone; the downstream D7 contract consumes deltas as versioned additive artifacts with 2B ids stable forever; the historical posture (bot-committed `Ontology/` CSVs in `.GIS`/`.MIMIC`/`.PSYCHIATRY`, README's "export of delta tables back to GitHub") was exactly this; and `release-vocab.yml` does a plain checkout and zips `Ontology/` — it only ever worked on committed deltas.

**Consequences.** No vocabulary currently has a committed baseline, and none is blessed by this ADR. EU2_Flowsheets' untracked working-tree `Ontology/*.csv` deltas are **not a commit candidate** (ruled out of scope by Daniel, 2026-07-23 — see Resolved during review): they are LLM-mapping-campaign output whose SSSOM is incomplete, failing the provenance-completeness gate above. EU2's baseline arrives through the Builder this ADR specifies, in sequence: this ADR rules the contract → the datamappings-ingest track converts the legacy datamappings document to SSSOM for Epic and runs the EU2 NS-mint through the fixed Builder → that corpus is committed as EU2's baseline → #607 closes. The queued post-April EU1_CDW NS-mint (~36.5k NS concepts) follows the same lifecycle: seed → build → diff → promote → commit. **Repo rule (new):** the committed refs are the only reviewable surface — code review, adversarial review, and drift checks compare against committed history, never against another session's working tree; uncommitted WIP on the shared main checkout is not a design posture and must not be treated as one (this rule exists because working-tree WIP already caused one false review finding on the eu1 branch).

**Alternatives rejected.** *Deltas as ephemeral build artifacts, rebuilt at release time:* requires a deterministic pipeline (stable ordering, frozen dates, seeded state) that does not exist and — per D6 — is not worth building, and it would make the release process itself capable of re-minting ids, violating the enterprise stable-forever contract. *Deltas stored outside git (S3, GitHub Release assets only):* loses the PR review gate, the diff-deltas drift check against history, and the public-repo distribution surface documented in `.MIMIC/Ontology/readme.md`.

### D3 — The build never writes to `Ontology/`; promotion is an explicit, gated release act

**Decision.** `execute-pipeline.sh` writes build output to `/tmp/output` (host `./output/`, gitignored) and **stops there**. Publication into `<VOCAB>/Ontology/` happens via a new explicit step — `scripts/promote-deltas.sh <VOCAB>` — which (1) runs the drift diff (`scripts/diff-deltas.sh`, hardened per D6.5) against the committed `Ontology/` baseline, (2) surfaces the drift summary (row deltas, new/removed codes, id ranges from `update_log.csv`), and (3) copies `output/* → <VOCAB>/Ontology/` only on explicit confirmation (`--apply`). Committing the promoted files (normally via PR) is the release-defining human act. The cleanup branch's unconditional `cp` tail block in `execute-pipeline.sh` is **dropped** (see Disposition table).

**Rationale.** Three reasons, in strength order. First, D2 makes `Ontology/` the id-registry-of-record; a build that can silently produce duplicates (the exact bug class #609 fixes; the S-side variant persists until D9's retirement of the S source-item mint lands) must not write the record unattended. Second, an unconditional in-build `cp` mechanically destroys the drift check: `diff-deltas.sh` compares the fresh build against the **on-disk working-tree** `<VOCAB>/Ontology/` (`diff-deltas.sh:28-29` — despite the `COMMITTED` variable name, no git call exists in the script), so a build that has already `cp`'d over `Ontology/` diffs the output against itself and always reads clean; the only remaining review surface would be `git diff`, dirtied on every debugging rebuild. Third, the transferred kitchen principle: the build is a refresh, the promoted-and-committed delta set is the release; a refresh must not write the release surface (§3.7), and the shared build engine is enablement the release consumes (§3.6).

**Placement and phasing (ruled during review; outcome recorded 2026-07-23).** The review ruling was that `promote-deltas.sh` land in the cleanup branch; events overtook it — the cleanup work merged as PR #3 before promote was written, so `promote-deltas.sh` shipped as its own follow-up **PR #4 (merged)** from branch `chore/cvb-promote-deltas` (beb2fa6, written and exercised on all six code paths). The ruling's substance was implemented as specified: the script displays the drift output, enforces diff-before-apply ordering, copies `output/*` (delta CSVs + `restore.sql` + `update_log.csv`) into `<VOCAB>/Ontology/` only on explicit `--apply`, and never commits. One implementation finding worth recording: `diff-deltas.sh` was committed mode 100644 (non-executable), so direct invocation dies with "Permission denied" — and the first promote draft swallowed that failure as advisory and copied anyway with the drift check never run. The landed promote invokes it via `bash` and **hard-refuses `--apply` on any non-zero exit** — correct today, because `diff-deltas.sh` exits 0 even on drift, so non-zero can only mean "the check didn't run"; the D6.5 hardening will invert that meaning to also cover real drift (the script carries a comment flagging this), and it slots in behind the same promote interface without changing it.

**Consequences.** #607 is fixed at the correct layer: not "the build now populates Ontology/" but "a promote step exists and the runbook says builds end with promote+commit when the output is meant to ship." `_TEMPLATE`'s and the live packages' READMEs get the promote step added to their pipeline runbooks. Local iteration stays cheap — rebuild as often as you like, `Ontology/` never moves until you promote. The legacy CI copy-back pattern (`cp` + `git-integration.js`) is formally retired, not resurrected.

**Alternatives rejected.** *Land the in-build `cp` (cleanup branch as proposed):* fastest reconnection of build→release, and defensible under a "generated files in tree, review the git diff" workflow — rejected because it neuters diff-deltas.sh's committed-vs-fresh comparison, dirties the record surface on every dev rebuild, and puts the one unattended write exactly where corruption is most expensive. *Resurrect CI auto-commit (git-integration.js pattern):* removes the human gate entirely; the archived vocabs prove it "works", but it predates the id-registry-of-record understanding and the enterprise stable-forever contract. *Pure manual `cp` with no script:* loses the enforced diff-first ordering, which is the actual gate.

### D4 — The named-interval contract (codifies the Daniel/EU1_CDW precedent)

**Decision.** The concept-id space contract, normative for all CVB code:

- **`id-registry.csv` at repo root is the sole allocation authority.** The Excel-era `twoB_ranges`/`ReservedConceptRanges` sheets are prototype, zero authority. The stale "Reserved Ranges" table in `README.md` is corrected to point at the registry.
- **All ranges are half-open `[min, max)`**: min inclusive, max exclusive, max never a usable id.
- **NS sits above S** within each vocab's 1M block: `S = [ID_RANGE_MIN, ID_RANGE_MAX)`, `NS = [NS_RANGE_MIN, NS_RANGE_MAX)`, with `NS_RANGE_MIN = ID_RANGE_MAX` (adjacent, non-overlapping) and `NS_RANGE_MAX` = the next block's `ID_RANGE_MIN`.
- **S ids count down** from `ID_RANGE_START` (= `ID_RANGE_MAX − 115`; the top 115 ids are the admin buffer where `VOCAB_CONCEPT_ID = ID_RANGE_MAX − 1` lives) toward `ID_RANGE_MIN`. **NS ids count up** from `NS_RANGE_MIN` toward `NS_RANGE_MAX`.
- **Three named intervals**, each with declared consumers:

| Named interval | Definition | Consumed by |
|---|---|---|
| `S_RANGE` | `[ID_RANGE_MIN, ID_RANGE_MAX)` | `revert-id-sequence.sql` (sequence bounds + seed), `update-standard.sql` (via the sequence) — after D9, the automated pipeline does not mint source items here **today** (admin/general concepts via `create-general-concepts.sql` only); `S_RANGE` stays **reserved** in `id-registry.csv` — allocation unchanged, no re-carving — for the future deliberate standard-minting capability per D9.4. |
| `NS_RANGE` | `[NS_RANGE_MIN, NS_RANGE_MAX)` | `update-nonstandard.sql` (max-existing lookup + assignment ceiling) |
| `FULL_SPAN` | `[ID_RANGE_MIN, NS_RANGE_MAX)` | `evaluate-difference.sql` (both S and NS existence joins — each self-selects on `standard_concept`), `create-delta-tables.sql` (all six range-gated companion tables) |

- **Every shared SQL file declares its interval in its header** (e.g. `-- Expects FULL_SPAN: id_range_min=ID_RANGE_MIN, id_range_max=NS_RANGE_MAX`), and `execute-pipeline.sh` passes **distinctly named psql vars** per interval (`s_range_min/s_range_max`, `ns_range_min/ns_range_max`, `full_range_min/full_range_max`) instead of overloading one `id_range_min/max` pair with three meanings across steps.

**Rationale.** The #606/#609 bug class existed because the semantics lived nowhere: `NS_RANGE_MIN = ID_RANGE_MAX` is a *boundary*, and a step wanting the *union* was handed the *gap*. Renaming the psql vars makes the empty-gap wiring unwritable — you cannot pass `(ns_range_min, id_range_max)` to a step whose parameters are `full_range_min/full_range_max` without it being visibly wrong. The half-open/NS-above-S/registry-sole-authority terms codify exactly the 2026-07-16 EU1_CDW allocation precedent (`EU1_CDW,2003,2003000000,2003500000,2003500000,2004000000` — 2004000000 never usable), now a committed `id-registry.csv` row on `main` (the EU1_CDW merge, 8f2ef0b), which all active registry rows (Winship, EU2, BHC, EU1_CDW) satisfy.

**Consequences.** The var rename touches `execute-pipeline.sh` and the headers/`:var` references of the shared SQL — mechanical, but it is a *contract* change and belongs in its own follow-up chore, not the pending cleanup branch (which fixes values under the existing names; see Disposition). `new-vocab.sh` already derives conformant ranges; it gains no new math, only the header-comment contract statement.

**Alternatives rejected.** *Keep one overloaded `id_range_min/max` pair with better comments:* comments are what we had (`update-nonstandard.sql` even documents the adjacency) and the gap still got wired in. *Closed intervals `[min, max]`:* contradicts the registry header, the EU1_CDW precedent, and would make the shared boundary `S_max == NS_min` a genuine double-claim. *Per-step bespoke ranges:* the three named intervals are exhaustive; more granularity adds surface without removing any bug class.

### D5 — Boundary semantics and guards: min-inclusive filters, NS exhaustion guard, archived inverted ranges frozen

**Decision.**

1. **All range predicates become `>= :min AND < :max`.** Today every parameterized filter is strict on both ends (`> min AND < max`), which is off-by-one at the **low** end under the half-open contract: a concept at exactly `id == min` is invisible to `evaluate-difference.sql` and silently dropped from every range-gated delta table — and the S sequence (`MINVALUE :id_range_min`, inclusive) *can* mint exactly that id at range fill, a proven self-inconsistency. The `< max` side is already correct for half-open and does not change. Files touched: `evaluate-difference.sql:21,88`, `create-delta-tables.sql:17-27`, `revert-id-sequence.sql:15`, `update-nonstandard.sql:46`.
2. **NS assignment gains an exhaustion guard.** `update-nonstandard.sql`'s `row_number() + max(existing)` arithmetic has no ceiling: on range fill it silently mints ids `>= NS_RANGE_MAX`, which under the adjacency rule is **the next vocabulary's `ID_RANGE_MIN` — a cross-vocab concept-id collision**. The step must assert `max(assigned id) < :ns_range_max` and abort the build with an explicit error otherwise. (The S side already fails hard by accident — the descending sequence has no `CYCLE`, so `nextval` errors at `MINVALUE` — document that as the intended behavior rather than an accident. Under D9's current posture the automated S mint serves admin/general concepts only, so S-side exhaustion is a near-impossibility in practice today — revisit if the future deliberate standard-minting capability (D9.4) is activated; the NS guard is the load-bearing one, since NS carries every source item.)
3. **The archived inverted ranges (MIMIC, PSYCHIATRY, GIS: NS *below* S in `id-registry.csv`) are grandfathered-frozen.** They keep their registry rows (the rows still prevent re-allocation of that id space) but are annotated with registry comment lines as legacy-inverted, non-conformant, and not a template for anything. Any revival of an archived vocab requires a fresh allocation under the current NS-above-S convention; the old blocks stay retired.
4. The hardcoded `concept_id > 2000000000` in `evaluate-difference.sql:66-72` feeds `SRC_DESC_MATCH`, a table with zero downstream consumers — **dead code**. It is removed (the DELETE and the table) rather than parameterized; `2000000000` remains the documented global custom-space floor where a check is genuinely cross-vocab (e.g. `hard-reset.sql`).

**Rationale.** Each item makes a bug class unrepresentable or loudly fatal instead of silent: (1) closes the assigner-can-mint-what-filters-drop hole; (2) converts the worst possible failure — silent cross-vocab id collision, which would poison a *neighboring* vocabulary's published ids — into a build abort; (3) prevents the inverted layout from ever being copied while preserving collision protection; (4) deletes an attractive nuisance instead of blessing it with parameters.

**Consequences.** These are shared-SQL changes and belong in a follow-up chore alongside D4's var rename (one "interval contract implementation" branch), not the pending cleanup branch. Behavior change from (1) is nil today (no concept currently sits at any `min`) but correct at range fill. (2) requires choosing a psql abort idiom (`DO $$ ... RAISE $$` or an `\if` check); implementation detail, not contract.

**Alternatives rejected.** *Fix off-by-one by shifting the registry mins down one:* rewrites the allocation authority to fit buggy filters — backwards. *NS exhaustion guard as a post-build check in `execute-pipeline.sh`:* too late; the inserts have already happened by then. *Deleting the inverted registry rows:* forfeits the only machine-readable record that those 2B blocks were ever used, inviting re-allocation collisions with the archived vocabs' published concept ids.

### D6 — Re-runnability contract: id-stability, not byte-determinism

**Decision.** A CVB build is **re-runnable by contract** with this meaning: *run against a database whose `vocab.concept` contains all previously committed custom concepts for the vocab, a rebuild from an unchanged `mapping.csv` mints zero new concepts and changes no existing ids.* The contract is **id-stability**, not byte-identical output — `now()::date` valid dates and heap-order row export mean the CSVs may differ textually run-to-run even when semantically identical. Requirements to make the contract true, and their status:

1. `evaluate-difference.sql` receives `FULL_SPAN` (the #609 fix) so the NS existing-concept guard (`DELETE ... WHERE concept_name IS NOT NULL`) actually fires. **Lands in the cleanup branch — verified safe** (see Disposition).
2. **The S source-item mint path is retired (supersedes the originally drafted "add the missing S-side guard").** The original defect stands as diagnosis: the S-side `co` join in `evaluate-difference.sql:16-26` was never wired to a `WHERE co.concept_id IS NULL`, no downstream reads any `co` column, and a re-run recreates all S concepts with fresh descending ids. But D9 removes the disease rather than guarding it — the automated pipeline mints no S source items, so no S re-run duplication is possible in the current model. The backlog item re-scopes from "add the S guard" to "retire the automated S source-item mint path" (`concept_check_s`/`update-standard.sql` for source items) within the resolution-model implementation. If the future deliberate standard-minting capability (D9.4) is activated, its consult must rule re-run semantics for that path as part of its design.
3. **The DB must be seeded before an incremental build.** A fresh Postgres volume (or post-`hard-reset.sql`) contains no custom rows, so even a fully-guarded build would re-mint everything with new ids. A `scripts/seed-from-ontology.sh <VOCAB>` (load the committed delta CSVs back into `vocab.*`) becomes the sanctioned path from "fresh DB" to "buildable state"; the runbook rule is: **never run an incremental build for a vocab with committed deltas against an unseeded DB.** `hard-reset.sql` + rebuild-from-scratch remains available but is a *re-mint*, only legitimate before any deltas have shipped.
4. Delta exports gain `ORDER BY` (stable sort on the natural key of each table) so that committed diffs are meaningful row-wise, not dominated by heap-order noise. Cheap, no semantic effect.
5. **`diff-deltas.sh` is hardened into a real drift oracle.** As written it cannot serve as the contract's acceptance test: it diffs against the on-disk working tree, not git (`:28-29`); it is advisory-only (exits 0 on drift; only missing-arg/dir errors are non-zero, `:21,:33,:38`); its content diff runs only when row *counts* changed (`has_changes` guard at `:108`) and only for three of the delta files (`:111`), so a counts-unchanged, dates-only rebuild reports all-zero without ever comparing content; its whole-line `comm` comparison flags every `now()::date` restamp as paired new/removed rows; and `head -20` silently truncates. The hardened version must: (a) diff against the committed baseline via git (`git show HEAD:<path>` or equivalent), (b) normalize or exclude volatile columns (`valid_start_date`, build-date `vocabulary_version`), (c) compare **all** delta files unconditionally, and (d) exit non-zero on any drift so `promote-deltas.sh` (D3) and future CI can gate on it — noting that promote already hard-refuses `--apply` on non-zero exit, so this inversion of meaning (from "didn't run" to "didn't run OR real drift") composes with the landed interface. Also fix the file mode: `diff-deltas.sh` is committed 100644 (non-executable), which is how the drift check once silently failed to run at all (see D3). `sort`-before-`comm` already neutralizes row order, which (4) additionally fixes at the source.

Full byte-determinism (frozen dates, deterministic id handout order) is **explicitly not pursued**: with committed deltas as the registry of record (D2) and id-stability guaranteed by seeding + guards, determinism buys nothing that the promote gate does not already provide, and freezing `valid_start_date` semantics would falsify real vocabulary provenance.

**Rationale.** The empty-interval bug was latent on first build and fatal on build #2 precisely because nobody had stated whether build #2 was a supported operation. Stating the contract (and what it requires) turns "it happened to work" into an invariant with named preconditions.

**Consequences.** New issues: S-side guard; seed script; export ORDER BY; diff-deltas hardening. The runbook ordering becomes: seed (if fresh DB) → build → diff → promote → commit. The **acceptance test of the contract** is the hardened `diff-deltas.sh` (D6.5): after a no-change rebuild on a seeded DB it must exit zero with no drift reported; today's script cannot perform that check and must not be cited as evidence the contract holds.

**Alternatives rejected.** *Full determinism (ORDER BY on id assignment, injected build date):* high effort, ongoing tax on every SQL change, and it papers over the real invariant — ids are stable because state is durable, not because the function is pure. *Declaring builds one-shot (never re-runnable):* contradicts the pipeline's own incremental design (sequence resume, existence joins) and makes every mapping-sheet update a re-mint, violating the stable-forever contract.

### D7 — One canonical copy: finish the FinOMOP extraction, gate the residue

**Decision.** The rule: **no pipeline logic lives in a per-vocab copy; a fix that applies to more than one vocabulary must land in a shared file.** Mechanically, in a follow-up chore:

1. `execute-pipeline.sh` and `revert-db.sh` move to repo-root `Builder/` as single canonical copies. Each `<VOCAB>/Builder/` keeps a **2-line shim** that `exec`s the canonical script with its own `VOCAB_DIR` (Option B from exploration) — the `docker compose run runner <VOCAB>/Builder/execute-pipeline.sh` invocation and all documented runbooks keep working, and a 2-line shim has nothing to drift.
2. The hybrid files `source-ddl.sql` and `load-source.sql` are split: the genuinely per-vocab head (the `temp.mapping` DDL and CSV-shaped load, which must match each vocab's sheet columns) stays local; the shared tail (the `temp.source_to_update` reviewer/metadata boilerplate — the `author_label` block, `temp.vocab_logger`) is extracted into `Builder/sql/shared/` include files pulled in via psql `\i` with repo-relative paths (the whole repo is one bind mount at `/workspace`, so paths resolve identically in-container).
3. A **CI drift gate** (new job in an existing workflow or a small dedicated one) fails any PR where a `<VOCAB>/Builder/` shim or a `_TEMPLATE/Builder/` file differs from its canonical counterpart, and where `_TEMPLATE`'s shim differs from the one `new-vocab.sh` would produce.
4. The dead legacy workflows `build-{gis,mimic,psychiatry}-vocab.yml` (trigger paths archived, reference `git-integration.js`) are deleted.
5. `new-vocab.sh` stops copying pipeline logic it no longer needs to copy; `_TEMPLATE/` shrinks to: the shims, the three designed-per-vocab SQL files (`create-general-concepts.sql` + the per-vocab heads of `source-ddl.sql`/`load-source.sql`), `Mappings/`, `Ontology/.gitkeep`, `README.md`, `vocab.env` generation.

**Rationale.** Drift here is a proven recurring disease, not a hypothesis: the three archived vocabs forked the full pipeline and diverged on 6+ "identical" files; the FinOMOP refactor (a48e444) cured 12 of ~17 files by extraction to `Builder/sql/shared/`; the disease then recurred on exactly the 5 residual per-vocab files — `_TEMPLATE` froze at 28b8b88 while EU2's real fixes landed only in EU2's copies at 48bb5ae, and EU1_CDW was provably scaffolded from EU2, not `_TEMPLATE`, because developers already knew the template was the least-correct copy. The extraction mechanism (one copy on disk, resolved by path at runtime) already exists and works; this decision finishes it. The CI gate exists because the archives prove that "please don't edit the copies" does not survive contact with a deadline.

**Consequences.** The pending cleanup branch's manual re-sync **lands as-is** (it is correct and it makes `_TEMPLATE/Builder ≡ EU2/Builder` modulo the one designed-per-vocab file — the right end state for the extraction to start from). The structural work (shim move, include split, CI gate, dead-workflow deletion) is a follow-up chore branch, deliberately not blocking the bugfix. EU1_CDW is merged to `main` (merge commit 8f2ef0b), so its Builder is converted to shims from day one of the extraction chore — no branch reconciliation step exists.

**Alternatives rejected.** *Option A (move scripts to root, change invocation to `Builder/execute-pipeline.sh VOCAB`):* cleanest end-state but churns every runbook, README, and muscle memory for zero drift-prevention gain over the shim. *Option C (symlinks):* fragile across `cp -r` in `new-vocab.sh`, zip packaging, and any Windows contributor. *Option D alone (keep copies, CI diff-gate only):* detects drift but preserves the mechanism that creates it; the gate is a backstop, not the fix. *`_TEMPLATE` as single source with packages forbidden to diverge:* backwards — the template is downstream of reality (it froze while EU2 advanced); canonical copies must live where fixes land, i.e. shared paths, with `_TEMPLATE` holding only what is genuinely per-vocab.

### D8 — Versioning: one release identity, calendar-dated, manually dispatched

**Decision.** Three uncoordinated version namespaces exist today: repo git tags (semver-flavored milestones, `v0.3.0`), release versions (`package-release.sh` defaults to calendar `YYYY.MM.DD`, workflow re-tags `v${VERSION}`), and per-vocab `vocabulary_version` strings inside `vocabulary_delta.csv` (build dates). Ruling:

1. **The delta-release identity is the calendar version `YYYY.MM.DD`**, cut via `workflow_dispatch` only. The `push: tags: ['v*']` trigger is **removed** from `release-vocab.yml` — as wired, any semver milestone tag (like the existing `v0.3.0`) silently cuts a full vocabulary release, which is a footgun, and it welds the milestone namespace to the release namespace.
2. Milestone git tags remain free-form and cease to have release side effects.
3. `vocabulary_version` (per-vocab build date inside the data) is provenance, not release identity; release notes must state each packaged vocab's `vocabulary_version` so consumers can tie a zip to the data snapshot it contains.
4. Repo-wide packaging (one release event zips every eligible vocab) is **accepted for now** as a documented limitation — with one live vocab it is harmless. Per-vocab release cadence is deferred to a future consult when a second live vocab makes it real.

**Rationale.** The incoherence is real but cheap to fix at the trigger/labeling layer; inventing a per-vocab semver scheme now would be speculative. Calendar versions match what the tooling already defaults to and what a "frozen data deliverable at a point in time" (kitchen ADR §1) naturally carries.

**Consequences.** One-line workflow change (drop the tag trigger); release-notes convention documented in the ADR and `README.md`. No change to `package-release.sh` naming (`{VOCAB}-v{VERSION}.zip`).

**Alternatives rejected.** *Per-vocab semver now:* no second live vocab to justify the machinery; revisit via consult. *Keep the tag trigger:* preserves the proven footgun.

### D9 — Resolution model: NS-only automated mint, one concept per source code, zero by omission; standard-minting reserved as a deliberate future capability (ruled by Daniel during review, 2026-07-23; plank 4 amended per Daniel, round 5)

**Decision.**

1. **Invariant: one concept_id per `(vocabulary_id, concept_code)`.** Enforced as a build-time uniqueness gate in the pipeline — fail-loud, same posture as D5's NS exhaustion guard.
2. **NS-only mint.** Every source code mints **exactly one** custom concept: non-standard, in `NS_RANGE`. `exactMatch` → the NS concept gets a `Maps to` edge to the Athena target (plus the reciprocal `Mapped from`). `noMatch` → the NS concept gets **no mapping edge at all**.
3. **The zero is by omission, not data.** `concept_relationship_delta` **never** contains edges to concept 0 (Daniel, verbatim intent: "concept_relationship_delta will NOT push 0"). A noMatch item's "maps to 0" materializes downstream — ETL resolves the *absent* mapping to `concept_id = 0` — and later curation **adds** the `Maps to` edge additively: a mapping update, never a concept replacement. `source_to_concept_map_delta`, as the deprecated-compat projection (enterprise ADR D6), MAY carry explicit `target_concept_id = 0` rows for noMatch per STCM convention, so legacy STCM consumers stay self-contained; the CR-delta constraint is the hard one.
4. **The automated per-row pipeline mints NS-only — today.** Custom Standard minting is a **reserved future capability**, not a permanent prohibition, with two named use cases (Daniel, verbatim in substance): (a) deliberately minting new **local standard** concepts for rows Emory wants as canonical local standards, and (b) **de-standardizing** an OHDSI Vocab WG concept and standardizing an Emory replacement. Neither is pushed as of yet; both are deliberate, human-adjudicated acts — never an automatic side effect of a sheet build (consistent with the layered-vocab phase posture: local de-standardization/supersession deferred to phase 2+ with human adjudication). Until then, `S_RANGE` mints only vocabulary-admin/general concepts (`create-general-concepts.sql`: the vocabulary concept at top-of-range and kin), and the automated S source-item mint machinery is retired. `S_RANGE` stays **reserved** in `id-registry.csv` — allocation unchanged, no re-carving — precisely *for* that future standard-minting capability, plus today's admin concepts. **Deliberately not ruled here:** the design of the future S-mint path — including how the `(vocabulary_id, concept_code)` uniqueness invariant is preserved when a code that already has an NS concept gains a local standard (re-flag vs new code vs supersession edge), and the de-standardization adjudication workflow — goes to a future consult against this ADR's node when the need becomes real. The uniqueness invariant itself (plank 1) stays hard and unconditional throughout.

**Rationale.** The defect that forced the ruling: the dual-concept model mints two concept_ids for the same `(vocabulary_id, concept_code)` — verified in the March artifacts, where 2001471855 (S) and 2001555089 (NS) both carry `(EU2_Flowsheets, code 8)` — violating the OMOP convention that `(vocabulary_id, concept_code)` is unique. Beyond the uniqueness violation, a self-minted custom "standard" concept is a standing replacement liability: when a community concept later appears, the custom S must be deprecated-and-remapped, whereas an NS concept just gains or updates a `Maps to` edge — exactly the additive posture the downstream D7 contract ("phase 1 deltas are additive only") demands. The ruling generalizes the model the enterprise track already chose: the queued EU1_CDW run is already an NS-mint (~36.5k NS concepts + CR edges filling `*_source_concept_id`).

**Consequences.** Materially changes shared SQL — `evaluate-difference.sql`'s `concept_check_s` path, `update-standard.sql`, parts of `create-delta-tables.sql` — scheduled as the **resolution-model implementation**, folded into a single combined follow-up chore with the interval-contract work (same files; two branches would collide — see backlog). D6.2 (the missing S-side guard) is superseded: no *automated* S mint for source items means no S re-run duplication; the item re-scopes to "retire the automated S source-item mint path." The archived vocabs' committed Ontology sets DO contain dual-minted S concepts: grandfather-frozen exactly like D5.3 froze the inverted ranges — published, retired, not a template. No live vocab has a committed baseline, so nothing published is affected. The uncommitted `CONCEPT_RESOLUTION.md` WIP must be rewritten to this model (rider on open question 1).

**Alternatives rejected.** *Dual-concept model (S + NS per source item, the March WIP's table):* violates `(vocabulary_id, concept_code)` uniqueness and mints a replacement liability per item. *Automatic S-mint for noMatch items (custom standard until a community concept appears):* the same liability concentrated exactly where community concepts are most likely to arrive later, and replacement is not additive — rejected as *pipeline default*; deliberate, human-adjudicated local-standard minting remains the reserved capability of D9.4. *Explicit 0-target rows in `concept_relationship_delta`:* encodes absence as data; later curation would have to replace rows instead of adding one, and concept 0 edges are not community convention.

### D10 — The Postgres Builder is retired; CVB becomes the shared exchange, minting goes local (ruled by Daniel, 2026-07-24)

**Decision.** The dockerized Postgres Builder — `Builder/sql/shared/*`, the per-package `Builder/` copies, `execute-pipeline.sh`, `docker/` + `docker-compose.yml`, `promote-deltas.sh` / `diff-deltas.sh` / `package-release.sh`, `hard-reset.sql`, and `release-vocab.yml` — is **retired**. It no longer assigns official concept ids and no longer maintains a git-committed `Ontology/` record. The parked interval-resolution work (`chore/cvb-interval-resolution`, `128c39e`) is **abandoned, not landed**: it hardened a builder that is being removed. The resolution model it encoded (D9) is not lost — it is reimplemented in each site's local mint.

CVB's role is redefined as the **shared custom-vocabulary exchange** for the Tufts CHoRUS CVB implementers: SSSOM-compliant draft mappings in, ratified ontology exports out, and `id-registry.csv` as the shared range-allocation authority. **Minting is a local implementer's concern** — Emory's is its warehouse (Trino/dbt), documented in `emory_omop_enterprise`. The successor design is [`cvb_architecture.md`](cvb_architecture.md).

**Rationale.** The builder was built as the do-everything center of the repo: it loaded a licensed vocabulary bundle into its own Postgres, minted ids, and committed deltas back to git as the authoritative record. That model put the id-authority, the licensed-data dependency, and a destructive rebuild-in-place engine all inside the repo. The federation model relocates each of those: minting belongs to whichever infrastructure a site already runs (for Emory, the warehouse, where the vocabulary bundle and the mapping sheet already live side by side), and the shared surface shrinks to the interoperable minimum — drafts, exports, and range allocation. A second minting engine inside CVB would only reintroduce cross-engine drift (the exact disease D7 fought) and a second id-authority to keep reconciled.

**Consequences.**
- Most of D2 (git `Ontology/` as the id-registry-of-record), D3 (the promote gate), D5 (the Postgres SQL guards), D6 (Postgres re-runnability), D7 (Builder template drift), and D8's release workflow describe machinery that no longer runs. They stand as **history**, superseded by this decision and the federation architecture.
- `Ontology/` survives in *name* but changes meaning: it is now a **dated export of ratified items** (`…__YYYYMMDD`), not the source of truth and not written by an in-repo build. `Mappings/` is renamed `ontology_drafts/`.
- `id-registry.csv` and the SSSOM validator/CI survive and grow (community ranges; verify-on-contribute).
- `docs/ARCHITECTURE.md` (the as-built inventory) is updated to mark the Builder retired and to reflect the exchange model.

**Alternatives rejected.** *Keep the Postgres Builder as a portable second implementation for external users* — rejected: it is a second id-authority and a drift source, and external consumers need the published exports, not a builder to run. *Make the builder deterministic and warehouse-agnostic* — solves nothing the local mint doesn't already solve, at the cost of maintaining a retired engine.
